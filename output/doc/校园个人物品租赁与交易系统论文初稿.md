# 校园个人物品租赁与交易系统的设计与实现

> 本文档为毕业论文初稿，学院、专业、姓名、学号、指导教师等信息待填写。

## 摘要

随着高校学生学习、生活和社交场景的持续数字化，校园内部闲置物品的租赁与交易需求逐渐增加。传统的线下交易和普通二手平台在校园场景中存在信息分散、身份可信度不足、交易过程难追踪、纠纷处理缺少依据等问题。针对上述问题，本文设计并实现了一套面向校园用户的个人物品租赁与交易系统。系统以微信小程序作为学生端入口，以 Vue 3 管理后台作为运营管理端，以 Spring Boot 后端服务作为统一业务支撑，围绕物品发布、校园认证、订单流转、微信支付、信用评价、消息通知和后台审核等环节构建完整业务闭环。

系统后端采用 Java 21、Spring Boot 3.1、MyBatis-Plus、MySQL 与 Redis 实现业务处理和数据持久化，使用 JWT 完成用户端与后台端的身份鉴别和权限边界控制；支付模块基于微信支付 API v3 SDK 设计生产支付骨架，并在本地环境提供可测试的模拟支付网关；部署层面采用 Docker Compose 组织后端、管理端、MySQL、Redis 与 Nginx 服务，数据库结构通过 Flyway 进行版本化迁移。系统实现后，对订单流转、支付回调幂等、金额校验、物品审核、用户禁用、信用变更和后台权限等关键场景进行了测试。结果表明，系统能够较好满足校园租赁交易业务的基本需求，具备较清晰的模块边界和进一步生产化扩展的基础。

关键词：校园交易；微信小程序；Spring Boot；JWT；微信支付；Docker Compose

## Abstract

With the increasing digitalization of learning and daily-life scenarios on campus, the demand for leasing and trading idle personal items among students has become more prominent. Traditional offline transactions and general second-hand platforms often suffer from scattered information, weak identity trust, poor process traceability and insufficient dispute-handling evidence in campus scenarios. To address these problems, this thesis designs and implements a campus-oriented personal item leasing and trading system. The system uses a WeChat Mini Program as the student-side entry, a Vue 3 based administration portal for platform operation, and a Spring Boot backend as the unified business service. It forms a complete business loop around item publishing, campus verification, order circulation, WeChat payment, credit evaluation, message notification and administrative review.

The backend is developed with Java 21, Spring Boot 3.1, MyBatis-Plus, MySQL and Redis. JWT is used to distinguish client and administrator tokens and to enforce access-control boundaries. The payment module is designed on top of WeChat Pay API v3 SDK, while a local mock gateway is provided for testable payment state transitions. For deployment, Docker Compose is used to orchestrate backend, administration frontend, MySQL, Redis and Nginx services. Database schema evolution is managed by Flyway migrations. Tests are carried out for order transitions, payment callback idempotency, amount verification, item review, user disabling, credit changes and administrator permissions. The results show that the system satisfies the core requirements of campus leasing and trading scenarios and provides a solid foundation for further production-level improvement.

Key words: campus trading; WeChat Mini Program; Spring Boot; JWT; WeChat Pay; Docker Compose

## 1 绪论

### 1.1 研究背景

高校学生群体具有居住空间相对集中、学习生活用品种类丰富、短期使用需求明显等特点。教材、实验器材、摄影设备、运动器材、电子产品和生活用品等物品在不同学生之间存在较大的复用空间。传统闲置物品交易通常依赖班级群、朋友圈或线下告示，其优点是门槛低，但信息生命周期短、搜索效率低、交易记录分散，并且缺少统一的信用评价和纠纷追踪机制。对于租赁场景而言，物品归还、押金处理、损坏责任认定等问题比普通买卖更加复杂，因此更需要平台化的流程管理。

微信小程序具有免安装、触达成本低、适合校园轻量服务等优势，适合作为学生端应用入口。与此同时，平台运营方需要对用户身份、物品内容、订单异常、系统参数和数据统计进行统一管理。因此，构建一套由小程序端、管理端和后端服务共同组成的校园个人物品租赁与交易系统，既具有较强的应用价值，也能覆盖软件工程毕业设计中需求分析、系统设计、数据库设计、接口开发、权限控制、支付集成、测试部署等完整环节。

### 1.2 研究意义

从实际应用角度看，本系统能够提高校园闲置资源的流转效率，降低学生短期使用物品的成本，并通过校园认证、信用分、评价和后台审核机制改善陌生人交易中的信任问题。从工程实践角度看，系统采用前后端分离架构和容器化部署方式，综合运用了现代 Web 后端、移动端、小程序、支付接口、数据库迁移和持续集成等技术，具有较完整的工程训练意义。

### 1.3 国内外研究与应用现状

现有二手交易平台多面向社会公共用户，平台规模较大，交易品类丰富，但在校园垂直场景下往往无法充分利用校园身份、校区距离、课程教材周期和学生信用关系等信息。部分校园交易服务停留在信息发布层面，缺少订单状态、支付流水、租赁记录、评价和后台运营能力。与普通二手交易相比，校园租赁交易更强调短周期、近距离、可信身份和过程留痕，因此需要针对性地设计业务模型。

### 1.4 论文主要工作

本文主要完成以下工作：第一，分析校园个人物品租赁与交易业务的角色、流程和非功能需求；第二，设计小程序端、管理端、后端服务和数据库组成的总体架构；第三，实现用户认证、物品管理、订单流转、支付处理、信用评价、消息通知和后台权限等核心模块；第四，引入 JWT、Flyway、Docker Compose 等机制提升系统安全性、可维护性和部署一致性；第五，通过单元测试、构建验证和容器镜像构建验证系统功能的可用性。

## 2 相关技术概述

### 2.1 微信小程序技术

微信小程序提供了页面、组件、网络请求、文件上传、本地存储和支付调起等能力，适合构建轻量级移动应用。系统学生端采用小程序组织首页、物品详情、发布、订单、消息、个人中心和钱包等页面，通过统一请求封装向后端 API 发送数据，并在本地保存 token 与用户信息。非 release 环境保留演示数据，便于前端界面预览；release 环境则切换为真实接口。

### 2.2 Vue 3 与 TypeScript

管理端采用 Vue 3、TypeScript、Vite 和 Element Plus。Vue 3 的组合式 API 便于将列表查询、筛选条件、弹窗状态和表单处理集中组织；TypeScript 能在接口字段、订单状态、用户对象和系统配置等场景中提供类型约束；Vite 提供快速开发和构建能力。管理端主要面向平台运营人员，强调数据可视化、表格筛选、审核操作和异常处理。

### 2.3 Spring Boot 与 MyBatis-Plus

后端采用 Spring Boot 3.1 构建 REST API 服务，通过 Controller、Service、Mapper 和 Entity 分层组织代码。MyBatis-Plus 简化了常见数据表的增删改查和分页查询，适合本系统中用户、物品、订单、支付流水、消息、评价、信用记录等业务表的操作。业务规则集中在 Service 层实现，以减少 Controller 中的过程性逻辑。

### 2.4 MySQL、Redis 与 Flyway

MySQL 用于保存核心业务数据，Redis 用于支撑缓存和后续扩展。为了避免手工执行建表脚本造成环境差异，系统引入 Flyway，将初始数据库结构放入版本化 migration 中。这样在首次启动和重复启动时，数据库结构均可被稳定管理，利于多人协作和容器化部署。

### 2.5 JWT 鉴权与权限控制

系统包含学生用户和后台管理员两类身份。为了防止用户端和后台端权限混用，后端在 JWT 中加入 tokenType 字段，将 CLIENT token 与 ADMIN token 区分开来。统一的 JwtAuthenticationFilter 负责解析 Authorization 请求头，并根据 token 类型注入不同角色权限。用户端接口要求 CLIENT 身份，后台接口要求 ADMIN 身份，系统用户管理进一步要求 SUPER_ADMIN 权限。

### 2.6 微信支付 API v3 与本地支付网关

支付模块采用微信支付 API v3 SDK 作为生产支付能力基础。创建支付单时，系统校验订单归属、订单状态和支付金额，生成唯一 paymentNo，并返回小程序支付参数。支付回调需完成验签、解密、金额校验和幂等处理。由于本地开发环境通常缺少真实商户凭证，系统提供非生产 profile 下的 LocalPaymentGateway 和本地支付确认接口，以便测试完整支付状态机。

### 2.7 Docker Compose 与 Nginx

系统采用 Docker Compose 统一编排 MySQL、Redis、后端服务和管理端 Nginx。管理端构建后的静态文件由 Nginx 托管，上传文件使用 Docker volume 持久化，并通过 Nginx 暴露静态访问路径。该方式能够降低环境搭建成本，提高开发、测试和部署环境的一致性。

## 3 系统需求分析

### 3.1 用户角色分析

系统主要包含三类角色：普通学生用户、后台运营管理员和超级管理员。普通学生用户通过小程序完成登录、校园认证、浏览物品、发布物品、创建订单、支付、退款、消息沟通和评价等操作。后台运营管理员通过管理端处理物品审核、用户状态、订单异常、系统配置和数据统计等事务。超级管理员在运营管理员能力基础上，额外拥有系统用户管理权限，可创建、停用或重置后台账号。

### 3.2 功能需求分析

学生端功能包括：用户登录与校园信息维护、首页推荐和分类浏览、物品详情查看、物品发布和图片上传、订单创建和状态查看、支付与退款、消息列表和未读统计、评价与申诉、个人中心和钱包流水。后台端功能包括：用户列表、用户禁用与信用调整、物品审核通过或驳回、订单筛选与状态处理、平台统计、系统配置维护和系统用户管理。后端需为上述功能提供统一接口，并保证接口返回格式一致。

### 3.3 非功能需求分析

安全性方面，系统需区分用户端与后台端权限，禁止默认用户兜底，防止越权查看订单、消息和支付记录。可靠性方面，支付回调可能重复投递，系统必须保证幂等处理；订单状态和支付流水更新应在事务中保持一致。可维护性方面，配置项应从环境变量读取，数据库结构应版本化管理。可部署性方面，系统应支持 Docker Compose 一键启动，并提供生产配置和文件持久化策略。

### 3.4 业务流程分析

物品发布流程为：用户填写物品信息并上传图片，系统保存为待审核状态，管理员在后台审核通过后物品进入可交易状态，驳回时保留审核备注。订单流程为：买家选择物品并创建订单，订单进入待支付状态；支付成功后订单进入待交付或履约状态；租赁类订单可进入进行中、待归还验收和已完成；异常情况下可进入取消、纠纷或退款中状态。信用流程为：实名认证、完成交易、违约、差评和投诉成立等事件触发信用分变化，并记录信用变更流水。

## 4 系统总体设计

### 4.1 总体架构设计

系统采用前后端分离和分层服务架构。表现层由微信小程序和 Vue 管理端组成；业务服务层由 Spring Boot 提供 REST API、鉴权过滤、业务事务和第三方支付适配；数据层由 MySQL、Redis 和本地文件存储组成；部署层由 Docker Compose、Nginx 和环境变量配置组成。总体架构可描述为：小程序端和管理端通过 HTTP/JSON 访问后端 API，后端根据 JWT 判断身份和权限，业务服务通过 Mapper 操作数据库，并在支付、文件和消息等场景中调用对应基础设施。

图 4-1 系统总体架构（文字示意）：学生端小程序 / 管理端 Web -> Nginx/API 网关 -> Spring Boot 后端 -> MySQL、Redis、Uploads Volume、微信支付平台。

### 4.2 后端分层设计

后端采用 Controller、Service、Mapper、Entity 和 DTO 分层。Controller 负责参数接收和统一响应；Service 负责业务规则、事务边界和跨表协作；Mapper 负责数据库访问；Entity 与数据库表结构对应；DTO 用于登录、下单、支付、审核、评价等接口输入输出。该设计使接口层保持轻量，核心业务规则集中于服务层，便于测试和维护。

### 4.3 鉴权与权限边界设计

系统将登录接口、公开物品列表、物品详情、公开用户主页、评价列表、支付回调和 Swagger 文档配置为公开访问，其余接口按用户端和后台端分组鉴权。AuthContext 只提供 requireCurrentUserId、requireCurrentAdminId 和 getCurrentAdminIdOrNull，不再提供默认用户兜底方法。后台系统用户管理由 AdminAccessGuard 继续检查 SUPER_ADMIN 角色，从而避免普通运营账号越权管理后台用户。

### 4.4 核心模块划分

系统按业务职责划分为用户模块、物品模块、订单模块、支付模块、评价与信用模块、消息模块、后台管理模块、系统配置模块和部署运维模块。各模块通过明确的服务接口协作，例如订单模块负责订单状态和物品状态同步，支付模块负责支付流水和订单支付状态一致性，信用模块负责信用规则和信用记录写入。

### 4.5 支付状态机设计

支付模块将创建支付单、支付回调、支付查询、退款申请和本地支付确认分离。创建支付单时生成 PROCESSING 状态流水；回调或本地确认成功后，将流水更新为 SUCCESS，并在同一事务中推动订单进入 PAID 状态；金额不一致时记录失败原因并拒绝更新订单；重复回调发现支付流水已成功时直接返回，避免重复修改订单和发送状态通知。

## 5 数据库设计

### 5.1 数据库设计原则

数据库设计遵循业务实体清晰、状态字段可追踪、流水表可审计和逻辑删除可恢复的原则。用户、物品、订单、支付流水、评价、消息、信用记录和系统配置均独立建表。与订单相关的支付和信用变更使用流水表保存历史过程，而不是仅在订单表中保存最终结果，以便后续审计和纠纷处理。

### 5.2 主要数据表说明

用户表 user 保存微信 openid、昵称、头像、学号、院系、校区、信用分、认证状态和账号状态；系统用户表 system_user 保存后台账号、角色、状态和最近登录时间；物品表 item 保存标题、描述、图片、分类、租售类型、价格、押金、校区、发布者和审核状态；订单表 order 保存订单号、物品、买卖双方、订单类型、状态、金额、租期和交付方式；支付流水表 payment_record 保存 paymentNo、订单、用户、支付类型、金额、支付方式、交易流水号、状态和失败原因；评价表 review、消息表 message、信用记录表 credit_record 和系统配置表 system_config 分别支撑评价、通知、信用变更和配置持久化。

### 5.3 表关系设计

用户与物品是一对多关系，一个用户可以发布多个物品；物品与订单是一对多关系，一个物品可在不同时间段产生多个租赁订单，但出售类物品在有效交易中应避免重复下单；订单与支付流水是一对多关系，支付、退款和押金均可作为流水记录；订单与评价是一对多关系，买卖双方可基于已完成订单评价；用户与消息是一对多关系，消息通过 senderId 和 receiverId 表示发送方和接收方；用户与信用记录是一对多关系，用于追踪信用分变化。

### 5.4 状态字段设计

物品状态包括待审核、上架中、租赁中、已售出、已下架和已驳回。订单状态包括待支付、待交付、进行中、待归还验收、已完成、已取消、纠纷中和退款中。支付状态包括失败、成功和处理中。状态字段使用整数常量表示，在服务层通过统一方法转换为前端展示文本，既便于数据库存储，也便于前端展示和后台筛选。

| 表名 | 含义 | 关键字段 |
| --- | --- | --- |
| user | 学生用户表 | openid、student_id、credit_score、is_verified、status |
| system_user | 后台系统用户表 | username、password、display_name、role、status |
| item | 物品信息表 | title、images、type、price、deposit、campus、status、user_id |
| order | 订单表 | order_no、item_id、buyer_id、seller_id、type、status、total_amount |
| lease_record | 租赁记录表 | order_id、lease_start、lease_end、actual_return、status |
| payment_record | 支付流水表 | payment_no、order_id、type、amount、transaction_id、status |
| review | 评价表 | order_id、reviewer_id、reviewee_id、rating、content |
| message | 消息表 | sender_id、receiver_id、type、content、is_read |
| credit_record | 信用记录表 | user_id、score_change、before_score、after_score、reason |
| system_config | 系统配置表 | config_key、config_value、description |

## 6 系统详细设计与实现

### 6.1 用户与校园认证模块实现

用户模块提供小程序登录、个人信息查询、公开主页、个人资料维护、校园认证和后台用户管理等功能。登录成功后，后端生成 CLIENT token；后台管理员登录成功后生成 ADMIN token。校园认证信息包括学号、院系和校区，认证通过后可提高用户在平台中的可信度。用户状态被禁用后，系统禁止其继续访问受保护接口或进行交易操作。

### 6.2 物品发布与审核模块实现

物品发布由学生端提交标题、描述、分类、租售类型、价格、押金、校区和图片信息。后端保存物品时默认进入待审核状态。管理员在管理端查看物品列表和详情，可执行审核通过或驳回操作。审核通过后物品进入可交易状态，驳回时保存审核原因，便于发布者修改。系统还根据发布者认证状态、信用分和物品信息完整度生成审核提示，辅助管理员判断。

### 6.3 订单流转模块实现

订单模块在创建订单时首先校验物品是否存在、是否为当前用户本人发布、是否处于可交易状态，并根据租赁或出售类型计算总金额。租赁订单需要处理开始时间、租赁天数、结束时间和押金；出售订单则主要使用商品价格作为应付金额。订单创建后处于待支付状态，并向买卖双方发送系统消息。后续订单状态更新会同步租赁记录和物品状态，例如支付成功后租赁类物品进入租赁中，出售类物品进入已售出，订单取消或退款时根据其他有效订单决定物品是否恢复上架。

### 6.4 支付与退款模块实现

支付模块通过 PaymentService 统一处理创建支付、回调、查询、退款和本地确认。创建支付时，系统检查订单归属和待支付状态，生成唯一 paymentNo，并调用 PaymentGateway 返回小程序支付参数。生产环境由 WechatPayGateway 适配微信支付 API v3；非生产环境由 LocalPaymentGateway 返回本地支付参数。支付回调解析后按 out_trade_no 查找支付流水，校验金额是否一致，并根据交易状态更新流水。退款申请会校验订单状态，写入退款流水，并将订单推进至退款中。

### 6.5 信用评价模块实现

信用模块将实名认证、完成交易、好评、差评、违约和投诉成立等行为抽象为信用规则，并在 CreditService 中统一处理分值变化。信用分设置上下限，避免无限增长或扣减到负值。评价模块要求订单已完成且评价者属于订单相关方，避免无关用户评价。评价提交后会触发信用规则，并向被评价方发送系统消息。

### 6.6 消息与 WebSocket 模块实现

消息模块提供站内消息发送、分页查询、标记已读和未读统计。系统消息用于订单创建、订单状态更新、评价通知等场景；用户消息用于交易双方沟通。WebSocket 配置中加入 token 校验，未携带合法 token 的连接被拒绝或限制，从而避免匿名连接进入受保护消息通道。

### 6.7 后台管理模块实现

后台管理端包含首页、用户管理、物品审核、订单管理、统计报表、系统配置和系统用户管理等页面。用户管理页支持查看认证和信用信息、禁用用户和调整信用分；物品管理页支持按状态和关键词筛选，并执行审核操作；订单管理页支持状态筛选、详情查看和流程推进，并展示支付单号、支付状态和交易流水；系统配置页将轮播图、公告、分类、校区和风控规则保存到数据库。

### 6.8 部署与配置实现

系统配置文件通过环境变量读取数据库、Redis、JWT、微信支付和文件访问地址等参数。生产配置关闭 SQL 标准输出，降低日志级别，并要求密钥外置。Docker Compose 默认服务包括 lease-mysql、lease-redis、lease-backend 和 lease-admin-nginx。后端采用多阶段 Maven/JDK21 构建，管理端采用 Node 构建后由 Nginx 托管，上传文件保存在 Docker volume 中。

## 7 系统测试与结果分析

### 7.1 测试环境

系统在 Windows 开发环境下进行本地开发，后端使用 Docker Maven 镜像提供 JDK 21 测试环境，管理端使用 Node.js 进行构建验证，容器化验证使用 Docker Desktop 和 Docker Compose。后端测试主要采用 JUnit 与 Mockito，管理端通过 TypeScript 编译和 Vite 构建验证类型与页面资源。

### 7.2 功能测试

功能测试覆盖用户登录、物品发布与审核、订单创建、订单状态流转、支付创建、支付成功、重复支付回调、金额不一致、退款申请、评价提交、信用分变更、用户禁用和后台权限等场景。支付模块重点测试幂等处理，确保重复回调不会重复修改订单；金额校验测试确保回调金额与本地订单金额不一致时不会误将订单标记为已支付。

### 7.3 权限测试

权限测试重点验证用户端 token 不能访问后台接口，后台 token 不能冒充普通用户下单，未登录访问受保护接口返回 401，权限不足返回 403。超级管理员可以管理系统用户，普通运营账号不能执行系统用户管理操作。通过统一 JwtAuthenticationFilter 和 AuthContext，可避免 Controller 层各自实现鉴权造成的不一致。

### 7.4 构建与部署验证

系统提供 scripts/verify-dev.ps1 作为统一验证脚本，依次执行 Docker Compose 配置检查、JDK 21 后端测试、管理端构建和回归标记扫描。实际验证中，后端 15 个自动化测试全部通过，管理端 npm run build 通过，npm audit 在修复后无中高危漏洞，后端和管理端 Docker 镜像均可构建成功。构建过程中管理端存在单个 bundle 体积超过 500KB 的提示，该问题不影响功能，可在后续通过路由级拆包和 manualChunks 优化。

### 7.5 测试结果分析

测试结果表明，系统核心业务流程能够按预期运行。支付与订单之间的事务一致性、支付回调幂等、后台权限隔离和小程序登录守卫是本系统稳定性的关键。当前测试仍以单元测试和构建验证为主，后续可进一步引入 Testcontainers、MockMvc 和端到端测试，以覆盖真实数据库迁移、接口鉴权和前端交互流程。

| 测试项 | 测试内容 | 预期结果 |
| --- | --- | --- |
| 鉴权测试 | 未登录、CLIENT token、ADMIN token、SUPER_ADMIN 权限边界 | 返回 401/403 或允许访问符合预期 |
| 订单流转 | 待支付、已支付、进行中、待验收、已完成、取消、退款中 | 状态变化正确，物品状态同步 |
| 支付回调 | 重复回调、金额不一致、成功回调 | 幂等处理，金额异常不更新订单 |
| 物品审核 | 审核通过、审核驳回、上架下架 | 状态和审核备注正确 |
| 用户管理 | 用户禁用、信用分调整、公开主页访问 | 受保护操作被限制，信用上下限正确 |
| 构建部署 | JDK21 后端测试、管理端构建、Docker 镜像构建 | 构建通过，依赖审计无中高危漏洞 |

## 8 总结与展望

本文围绕校园个人物品租赁与交易场景，完成了一套包含微信小程序、管理后台和 Spring Boot 后端的系统设计与实现。系统从需求分析出发，设计了用户、物品、订单、支付、评价、信用、消息和后台管理等模块，并通过 JWT 鉴权、微信支付适配、本地支付网关、Flyway 数据库迁移和 Docker Compose 部署提升系统的工程完整性。实现结果表明，系统能够支持校园用户进行物品租赁与交易，并为平台运营方提供审核、统计和风控能力。

受时间和条件限制，系统仍有进一步完善空间。第一，真实微信商户凭证联调和生产回调压测尚需在正式环境中完成；第二，文件存储当前采用本地持久化卷，后续可接入 MinIO 或云对象存储；第三，推荐算法目前以规则和筛选为主，后续可结合用户行为实现个性化推荐；第四，纠纷仲裁、押金冻结和退款自动化还可以进一步细化；第五，测试体系可进一步扩展到端到端自动化测试和持续部署流水线。总体而言，本系统已形成较完整的校园租赁交易业务闭环，为后续生产化落地和功能扩展奠定了基础。
