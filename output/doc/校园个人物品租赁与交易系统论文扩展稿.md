# 校园个人物品租赁与交易系统的设计与实现

> 本文档为毕业论文扩展稿，学院、专业、姓名、学号、指导教师等信息待填写。

## 摘要

随着高校学生学习、生活和社交场景的持续数字化，校园内部闲置物品的租赁与交易需求逐渐增加。教材、实验器材、摄影设备、运动器材、电子产品和生活用品等物品在不同学生之间具有较强的复用价值，但传统线下交易和通用二手平台在校园场景中仍存在信息分散、身份可信度不足、交易过程难追踪、租赁纠纷缺少依据等问题。针对上述问题，本文设计并实现了一套面向校园用户的个人物品租赁与交易系统。系统以微信小程序作为学生端入口，以 Vue 3 管理后台作为运营管理端，以 Spring Boot 后端服务作为统一业务支撑，围绕物品发布、校园认证、订单流转、微信支付、信用评价、消息通知和后台审核等环节构建完整业务闭环。

系统后端采用 Java 21、Spring Boot 3.1、MyBatis-Plus、MySQL 与 Redis 实现业务处理和数据持久化，使用 JWT 完成用户端与后台端的身份鉴别和权限边界控制；支付模块基于微信支付 API v3 SDK 设计生产支付骨架，并在本地环境提供可测试的模拟支付网关；数据库结构通过 Flyway 进行版本化迁移；部署层面采用 Docker Compose 组织后端、管理端、MySQL、Redis 与 Nginx 服务。系统实现后，对订单流转、支付回调幂等、金额校验、物品审核、用户禁用、信用变更和后台权限等关键场景进行了测试。测试结果表明，系统能够较好满足校园租赁交易业务的基本需求，具备较清晰的模块边界、较完整的工程实现和进一步生产化扩展的基础。

关键词：校园交易；物品租赁；微信小程序；Spring Boot；JWT；微信支付；Docker Compose

## Abstract

With the continuous digitalization of learning and daily-life scenarios in universities, the demand for leasing and trading idle personal items among students has become increasingly prominent. Textbooks, laboratory equipment, cameras, sports equipment, electronic devices and daily necessities often have strong reuse value within a campus. However, traditional offline transactions and general second-hand platforms still suffer from scattered information, weak identity trust, poor process traceability and insufficient evidence for leasing disputes. To address these problems, this thesis designs and implements a campus-oriented personal item leasing and trading system. The system uses a WeChat Mini Program as the student-side entry, a Vue 3 based administration portal for platform operation, and a Spring Boot backend as the unified business service. It forms a complete business loop around item publishing, campus verification, order circulation, WeChat payment, credit evaluation, message notification and administrative review.

The backend is developed with Java 21, Spring Boot 3.1, MyBatis-Plus, MySQL and Redis. JWT is used to distinguish client and administrator tokens and to enforce access-control boundaries. The payment module is designed on top of WeChat Pay API v3 SDK, while a local mock gateway is provided for testable payment state transitions. Flyway is introduced to manage database schema migration, and Docker Compose is used to orchestrate backend, administration frontend, MySQL, Redis and Nginx services. Tests are carried out for order transitions, payment callback idempotency, amount verification, item review, user disabling, credit changes and administrator permissions. The results show that the system satisfies the core requirements of campus leasing and trading scenarios and provides a solid foundation for further production-level improvement.

Key words: campus trading; item leasing; WeChat Mini Program; Spring Boot; JWT; WeChat Pay; Docker Compose

## 1 绪论

### 1.1 研究背景

高校学生群体具有居住空间相对集中、学习生活用品种类丰富、短期使用需求明显等特点。在校园生活中，很多物品并非长期高频使用，例如摄影器材、运动器材、教材教辅、实验工具、演出服装、生活小电器等。这类物品如果只能通过购买方式获得，会造成较高的重复消费和资源闲置；如果能够在校内建立可信的租赁与交易渠道，则可以降低学生使用成本，提高物品利用率，并促进校园内部资源循环。
目前学生之间的闲置物品流转多依赖微信群、朋友圈、论坛或线下熟人介绍。此类方式虽然使用门槛较低，但信息缺少结构化管理，发布后容易被新消息覆盖，买卖双方很难按品类、校区、价格和信用情况快速筛选。更重要的是，普通信息发布渠道缺乏统一的身份认证、订单留痕、支付流水、评价反馈和纠纷处理机制。一旦出现物品损坏、逾期归还、付款争议或描述不符等问题，双方往往只能依赖聊天截图和个人协商解决，平台化治理能力不足。
与普通二手买卖相比，租赁业务对过程管理的要求更高。租赁订单不仅涉及支付金额，还涉及租期、押金、交付方式、归还验收和损坏责任认定。若没有统一的订单状态机和信用约束机制，租赁双方的信任成本较高，平台也难以及时发现异常交易。基于此，本文选择“校园个人物品租赁与交易系统”作为研究和设计对象，尝试将校园身份、物品审核、订单流程、支付流水和信用评价纳入统一系统。

### 1.2 研究意义

从应用价值看，本系统能够为学生提供一个低门槛、可信、可追踪的校园交易渠道。学生可以快速发布闲置物品，也可以按校区、品类、价格等条件查找所需物品；平台通过校园认证和信用分展示降低陌生人交易的不确定性，通过订单状态、支付记录和消息通知提高交易过程透明度。对于校园管理和平台运营而言，后台审核、用户管理、订单监控和统计报表有助于及时处理违规发布、异常订单和纠纷申诉。
从工程实践价值看，本系统覆盖了较完整的软件工程开发流程，包括需求分析、架构设计、数据库设计、接口设计、前后端开发、鉴权控制、支付集成、测试验证和容器化部署。系统采用微信小程序、Vue 3、Spring Boot、MySQL、Redis、Flyway、Docker Compose 等技术，能够体现现代 Web 应用和移动应用协同开发的典型特征。

### 1.3 国内外研究与应用现状

国内外已有大量面向公众的二手交易平台和租赁平台，例如综合类二手交易应用、社区交易平台和垂直租赁服务。此类平台用户规模大、商品种类丰富，但通常面向社会公众，交易双方地理距离、身份背景和交易习惯差异较大。对于校园场景而言，通用平台无法充分利用校园身份、校区距离、课程周期、学生信用和线下面交便利性等优势。
部分高校内部也存在论坛、表白墙、社群小程序等轻量交易方式，但多数停留在信息展示层面，缺少严格的订单状态管理和支付信用闭环。在租赁场景下，若仅提供信息发布，不记录租期、押金和归还验收状态，则很难支撑稳定运行。因此，校园交易系统需要在轻量易用和流程可控之间取得平衡。本文所实现的系统不是简单的信息发布工具，而是围绕发布、审核、下单、支付、履约、评价和信用建立相对完整的业务闭环。

### 1.4 本文主要工作

本文主要完成以下工作：第一，对校园个人物品租赁与交易场景进行需求分析，明确学生用户、运营管理员和超级管理员的功能边界；第二，设计小程序端、管理端、后端服务、数据库和部署环境组成的总体架构；第三，实现用户认证、物品发布审核、订单状态流转、支付与退款、信用评价、消息通知、后台统计和系统配置等核心功能；第四，引入 JWT 鉴权、微信支付 API v3、本地支付模拟网关、Flyway 数据库迁移和 Docker Compose 容器化部署，提高系统安全性和工程完整性；第五，对核心业务流程和权限边界进行测试，并分析系统当前不足和后续优化方向。

### 1.5 论文组织结构

全文共分为九章。第一章介绍研究背景、意义、现状和主要工作；第二章介绍系统使用的关键技术；第三章从角色、功能、非功能和可行性角度分析系统需求；第四章给出总体架构、模块划分和关键流程设计；第五章说明数据库表结构和关系；第六章详细描述主要功能模块的实现；第七章介绍测试方案和结果；第八章说明部署和运行维护设计；第九章总结全文并提出后续展望。

## 2 相关技术概述

### 2.1 微信小程序技术

微信小程序具有无需安装、入口丰富、加载较快、与微信生态结合紧密等特点，适合构建校园轻量应用。系统学生端采用小程序实现首页推荐、物品详情、发布物品、创建订单、订单列表、订单详情、消息中心、个人中心、钱包流水、校园认证和评价申诉等页面。小程序通过 wx.request 与后端 API 通信，通过 wx.uploadFile 完成图片上传，通过本地 storage 保存 token 和用户信息，通过 wx.requestPayment 调起微信支付能力。
在开发阶段，小程序还需要兼顾演示和真实接口调用。本系统将 API 地址和 WebSocket 地址抽取到统一环境配置中，开发环境默认访问本地后端，release 环境可配置真实域名。首页和消息页保留非 release 演示数据，便于在微信开发者工具中快速查看页面效果，但真实发布环境不再依赖模拟数据。

### 2.2 Vue 3 与 TypeScript

Vue 3 是当前常用的前端框架之一，组合式 API 能够更清晰地组织状态、计算属性和事件处理逻辑。管理端采用 Vue 3、TypeScript、Vite 和 Element Plus 构建。TypeScript 为用户、物品、订单、系统用户和系统配置等接口数据提供类型定义，减少字段拼写和数据类型错误。Vite 提供快速热更新和生产构建能力，Element Plus 提供表格、弹窗、提示和表单等后台管理常用组件。
管理端的设计目标与学生端不同。学生端强调移动端交互和流程简洁，管理端则强调信息密度、筛选效率和操作反馈。因此管理端页面以表格、筛选栏、指标卡片和详情弹窗为主，帮助管理员快速处理用户状态、物品审核、订单异常和系统配置。

### 2.3 Spring Boot 与 RESTful API

Spring Boot 能够简化 Java Web 项目的配置和依赖管理，适合构建中小型业务系统后端。系统后端基于 Spring Boot 3.1，将接口划分为用户、物品、订单、支付、消息、评价、后台认证、系统用户、统计和配置等 Controller。接口统一返回 code、message 和 data 字段，便于小程序和管理端统一处理成功、失败、未登录和无权限等情况。
RESTful API 设计强调资源和操作的清晰表达。本系统在保持原有业务路径的基础上，将登录、列表、详情、创建、状态更新、审核、支付创建、支付查询、退款等行为拆分为明确接口。Controller 只负责参数接收和响应包装，复杂业务逻辑放到 Service 层，避免接口层承担过多职责。

### 2.4 MyBatis-Plus 与数据访问

MyBatis-Plus 在 MyBatis 基础上提供了通用 Mapper、分页插件、条件构造器、逻辑删除和字段自动填充等能力，能够减少重复的 CRUD 代码。系统中的 User、Item、Order、PaymentRecord、Review、Message、CreditRecord、SystemUser 和 SystemConfig 均通过实体类与数据表对应。复杂查询使用 LambdaQueryWrapper 构造条件，分页查询使用 Page 对象承载结果。
为了保证业务规则不分散在数据访问层，Mapper 主要承担数据库读写职责，Service 层负责校验订单归属、判断状态是否可流转、处理信用规则和调用消息通知。这样既保留了 MyBatis-Plus 的开发效率，也避免了业务逻辑与 SQL 操作过度耦合。

### 2.5 JWT 与 Spring Security

JWT 是一种常见的无状态身份凭证。系统登录成功后由后端生成 token，前端在后续请求中通过 Authorization: Bearer 头携带。后端 JwtAuthenticationFilter 解析 token，读取 tokenType、userId、adminId、username 和 role 等声明，并根据 token 类型注入 ROLE_CLIENT、ROLE_ADMIN 或 ROLE_SUPER_ADMIN。
Spring Security 负责统一拦截受保护接口。系统仅放行登录、公开商品列表、商品详情、公开用户主页、用户评价、支付回调和接口文档等路径，其余路径按用户端和后台端分组鉴权。AuthContext 不再提供默认用户兜底方法，受保护业务必须显式要求当前用户或当前管理员身份，从而减少越权风险。

### 2.6 微信支付 API v3

微信支付 API v3 使用平台证书、商户私钥、API v3 密钥、回调验签和资源解密等机制保证支付安全。系统支付模块引入官方 Java SDK，生产环境由 WechatPayGateway 负责创建 JSAPI/小程序支付参数和解析支付通知。支付通知处理时需要根据 out_trade_no 查找本地支付流水，校验金额、交易状态和幂等性，并在事务中更新订单状态。
本地开发往往无法直接使用真实微信商户环境。为解决测试困难，系统提供 LocalPaymentGateway 和本地支付确认接口。该接口仅在非生产 profile 注册，前端检测到 LOCAL_PAY_SIGN 后弹出本地支付确认框，确认后调用后端本地接口推动真实支付状态机。这样既不破坏生产支付设计，又能在开发环境验证订单和支付的一致性。

### 2.7 Flyway 与数据库迁移

Flyway 是数据库版本迁移工具，能够按照版本号顺序执行 SQL migration。系统将初始 schema 拆分到 db/migration/V1__init_schema.sql 中，后续结构变更可以继续通过 V2、V3 等脚本管理。与传统手工执行 schema.sql 相比，Flyway 可以记录数据库当前版本，避免重复执行和环境差异。

### 2.8 Docker Compose 与容器化部署

Docker Compose 可通过一个配置文件编排多个服务。系统默认服务包括 MySQL、Redis、Spring Boot 后端和 Nginx 管理端。后端 Dockerfile 采用 Maven/JDK21 多阶段构建，构建产物运行在 JRE 镜像中；管理端 Dockerfile 先用 Node 构建静态文件，再由 Nginx 托管。文件上传目录通过 Docker volume 持久化，Nginx 对外暴露 uploads 静态路径。

## 3 系统需求分析

### 3.1 业务目标

系统目标是为校园用户提供一个可信、便捷、可追踪的物品租赁与交易平台。可信体现在校园身份认证、信用分、评价记录、后台审核和权限控制；便捷体现在微信小程序入口、移动端发布、图片上传、分类浏览和订单操作；可追踪体现在订单状态、支付流水、消息记录、信用记录和后台统计。系统不仅服务普通学生用户，还要为平台运营人员提供审核、监管和配置能力。

### 3.2 用户角色分析

普通学生用户是系统的主要使用者，可以浏览物品、查看发布者信用、发布闲置物品、创建租赁或交易订单、支付、申请退款、发送消息、提交评价和查看个人信用。后台运营管理员负责日常运营，包括用户管理、物品审核、订单监控、统计查看和系统配置。超级管理员在运营管理员基础上增加系统用户管理权限，可以创建后台账号、重置密码和停用账号。
角色划分的核心在于权限边界。学生用户不应访问后台统计和审核接口，后台管理员也不应冒充学生直接下单或支付。系统通过 tokenType 区分 CLIENT 和 ADMIN，并在业务层进一步校验订单、支付流水、消息和物品的资源归属。

### 3.3 学生端功能需求

学生端功能包括登录与认证、首页浏览、物品搜索和详情查看、物品发布、我的物品、订单创建、订单列表、订单详情、支付、退款、消息、评价、申诉、个人主页、钱包流水和帮助信息。学生发布物品时需填写标题、描述、图片、分类、租售类型、价格、押金和校区。创建订单时系统根据物品类型计算金额，租赁订单还需记录开始时间和租赁天数。支付成功后，订单状态和物品状态应同步变化。

### 3.4 管理端功能需求

管理端需要支持账号登录、首页数据概览、用户列表、用户禁用、信用处理、物品审核、订单筛选、订单详情、订单状态处理、统计报表、系统配置和系统用户管理。管理端页面应提供加载状态、空状态、错误提示和操作后刷新，保证管理员能够明确看到操作结果。订单详情中应展示支付状态、支付单号和交易流水，方便排查支付和订单不一致问题。

### 3.5 后端功能需求

后端需要提供统一 REST API，完成参数校验、身份认证、权限判断、业务事务、数据库访问、支付适配、文件上传、消息通知和系统配置持久化。所有接口响应格式保持统一，未登录返回业务码 401，权限不足返回业务码 403，业务异常返回可读错误信息。支付回调接口应允许微信支付平台匿名投递，但内部必须完成验签、解密和金额校验。

### 3.6 非功能需求

安全性方面，系统需要防止默认用户兜底、越权访问、后台账号滥用和支付伪造。可靠性方面，支付回调可能重复投递，系统必须保证幂等；订单状态、支付流水和物品状态应在事务内保持一致。易维护性方面，系统配置应外置到环境变量或数据库，数据库结构应版本化管理。可扩展性方面，支付网关、文件存储和推荐算法应保留替换空间。可部署性方面，应提供 Docker Compose 配置和统一验证脚本。

### 3.7 可行性分析

技术可行性方面，微信小程序、Vue 3、Spring Boot、MySQL、Redis 和 Docker Compose 均为成熟技术，相关文档和社区资料丰富，能够满足本系统开发需求。经济可行性方面，系统开发所需软件和依赖大多为开源工具，本地开发和演示部署成本较低；真实上线时主要成本来自服务器、域名、证书、微信支付商户和对象存储。操作可行性方面，学生端依托微信生态，用户学习成本低；管理端采用常见后台界面，运营人员可以通过表格和按钮完成审核与处理。法律和合规方面，系统需遵守个人信息保护、支付安全和平台内容管理要求，生产环境应进一步完善隐私协议、敏感信息脱敏和日志审计。

## 4 系统总体设计

### 4.1 设计原则

系统设计遵循分层清晰、权限明确、状态可追踪、配置外置和便于部署的原则。分层清晰要求前端、后端、数据访问和基础设施职责明确；权限明确要求用户端和后台端 token 不可混用；状态可追踪要求订单、支付、租赁、评价和信用变化都有记录；配置外置要求数据库密码、JWT 密钥、微信支付参数和文件访问地址不写死在代码中；便于部署要求通过 Docker Compose 尽量减少环境差异。

### 4.2 总体架构

系统采用前后端分离架构。学生通过微信小程序访问后端 API，管理员通过 Vue 管理端访问后端 API，Nginx 负责管理端静态资源托管和上传文件静态访问。后端 Spring Boot 服务承担业务处理、鉴权、事务和第三方支付适配，数据保存在 MySQL 中，Redis 用于缓存和后续扩展。
总体架构可以概括为：微信小程序和管理端作为表现层，通过 HTTP/JSON 与后端交互；Spring Boot 作为业务服务层，通过 Controller 接收请求，通过 Service 执行业务规则，通过 Mapper 访问 MySQL；支付网关、文件存储、WebSocket 和系统配置作为支撑模块；Docker Compose 负责组合运行环境。

### 4.3 后端分层结构

后端代码按照 Controller、Service、Mapper、Entity、DTO、Security、Config 和 Support 等包组织。Controller 负责路由和参数接收；Service 负责业务流程和事务；Mapper 负责数据库操作；Entity 对应数据库表；DTO 表示请求和响应数据；Security 包含 JWT 过滤器和异常处理；Support 包含 AuthContext 和 AdminAccessGuard 等辅助组件。该结构有利于将业务规则集中到服务层，也便于编写单元测试。

### 4.4 模块划分

系统主要模块包括用户认证模块、物品管理模块、订单管理模块、支付退款模块、评价信用模块、消息通知模块、后台管理模块、系统配置模块和部署运维模块。用户认证模块负责登录、token 和校园认证；物品模块负责发布、审核和上下架；订单模块负责创建和状态机；支付模块负责支付流水和回调；评价信用模块负责评分和信用分；消息模块负责站内通知；后台管理模块负责运营动作；系统配置模块负责分类、校区、公告和风控规则。

### 4.5 关键业务流程设计

物品发布流程为：学生填写物品信息并上传图片，后端保存为待审核，管理员审核通过后物品上架，驳回则保存原因。订单流程为：买家创建订单，系统校验物品和租期，订单进入待支付；支付成功后进入待交付；租赁订单可进入进行中、待归还验收和已完成；异常订单可进入取消、纠纷中或退款中。支付流程为：创建支付流水，调用支付网关获取支付参数，支付回调或本地确认成功后更新支付流水和订单。信用流程为：实名认证、完成交易、好评、差评、违约和投诉成立触发信用分变化。

### 4.6 安全设计

安全设计从身份、权限、资源归属和敏感配置四个方面展开。身份层面，系统使用 JWT 标识用户和管理员；权限层面，Spring Security 按路径限制接口访问；资源归属层面，订单详情、支付查询、退款、消息和文件上传等操作均需校验当前用户是否有权访问；敏感配置层面，JWT 密钥、数据库密码、微信支付私钥和 API v3 key 均通过环境变量或外部文件注入，不提交到仓库。

### 4.7 异常处理与统一响应设计

后端通过全局异常处理器捕获业务异常、未授权异常、权限不足异常和参数校验异常，统一返回 code、message 和 data 格式。小程序和管理端请求封装根据 code 和 HTTP 状态处理登录失效、权限不足、业务失败和网络错误。统一响应格式降低了前端处理复杂度，也便于后续接入接口文档和自动化测试。

## 5 数据库设计

### 5.1 概念结构设计

系统概念模型围绕用户、物品、订单、支付、评价、消息和信用展开。用户可以发布多个物品，也可以作为买家创建多个订单；物品属于发布者，一个物品可以产生多个租赁订单或一个有效出售订单；订单连接买家、卖家和物品，是支付、评价、消息和信用变更的重要依据；支付流水记录订单相关的支付、退款和押金；评价记录订单完成后的双方反馈；消息记录系统通知和用户沟通；信用记录保存信用分变化历史。

### 5.2 逻辑结构设计

数据库表设计采用业务实体表与流水表结合的方式。实体表如 user、item、order 保存当前业务状态；流水表如 payment_record、credit_record 保存历史过程。系统配置使用 system_config 表持久化，避免配置仅存在内存中。所有主要表包含 create_time、update_time 和 deleted 字段，支持时间追踪和逻辑删除。

### 5.3 主要数据表设计

user 表保存学生用户信息，包括 openid、昵称、头像、学号、院系、校区、信用分、认证状态和账号状态。item 表保存物品标题、描述、图片、分类、租售类型、价格、押金、校区、发布者、浏览数、收藏数和状态。order 表保存订单号、物品、买家、卖家、订单类型、状态、金额、押金、租期和备注。payment_record 表保存支付流水号、订单、用户、支付类型、金额、支付方式、交易流水号、状态和失败原因。review、message、credit_record 和 system_config 表分别支撑评价、消息、信用和配置。

### 5.4 状态字段设计

状态字段是本系统数据库设计的重点。物品状态包括待审核、上架中、租赁中、已售出、已下架和已驳回；订单状态包括待支付、待交付、进行中、待归还验收、已完成、已取消、纠纷中和退款中；支付状态包括失败、成功和处理中；后台用户状态包括启用和禁用。系统通过常量类集中定义状态值，并在服务层转换为中文状态文本，减少魔法数字分散。

### 5.5 数据一致性设计

订单、支付和物品状态之间存在强关联。支付成功时，不仅要更新 payment_record，还要更新 order 状态并同步 item 状态；退款申请时，需要写入退款流水并将订单推进到退款中；订单取消时，需要根据是否存在其他有效订单决定物品是否恢复上架。因此相关操作应放在事务中执行。对于支付回调，系统根据 paymentNo 判断流水是否已成功，若已成功则直接返回，避免重复回调导致状态重复推进。

### 5.6 数据库迁移设计

系统使用 Flyway 管理数据库结构。初始建表脚本放在 V1__init_schema.sql 中，后续新增字段或表结构调整应通过新的版本脚本完成。该方式可以保证不同开发环境、测试环境和生产环境的数据库结构一致，也有利于回滚和审计。相比在 Docker init 目录中手工维护 schema，Flyway 更适合应用服务驱动的持续演进。

## 6 系统详细设计与实现

### 6.1 用户认证与校园认证实现

用户端登录接口接收登录请求并返回用户信息和 CLIENT token。后台登录接口返回管理员信息和 ADMIN token。JWT 中包含 tokenType，用于区分普通用户和后台管理员。AuthContext 提供 requireCurrentUserId 和 requireCurrentAdminId 方法，业务代码必须显式获取当前身份，避免使用默认用户。
校园认证功能允许用户提交学号、院系和校区信息。认证信息与信用展示结合，能够提升用户主页可信度。用户被后台禁用后，系统拒绝其继续访问受保护接口或进行交易操作。后台用户由 system_user 表管理，超级管理员可以创建运营账号、重置密码和调整状态。

### 6.2 物品发布与审核实现

学生发布物品时，小程序提交标题、描述、图片、分类、租售类型、价格、押金和校区。后端检查必要字段后保存物品，默认状态为待审核。图片通过文件上传接口保存到 uploads 目录，返回 URL 使用 FILE_PUBLIC_BASE_URL 生成。
后台物品管理页面支持按关键字、类型、校区和状态筛选物品。管理员可以查看物品详情、发布者认证状态和信用信息，并执行审核通过或驳回。审核通过后物品进入上架中状态，驳回后记录审核原因。为了提高审核效率，后端根据物品完整度和发布者信用生成审核提示。

### 6.3 订单创建与状态流转实现

订单创建时，系统首先根据 itemId 查询物品，判断物品是否存在、是否为当前用户本人发布、是否处于上架状态。出售类物品需要检查是否已有有效交易订单，防止重复出售。租赁类订单需要解析开始时间、租赁天数和结束时间，并检查同一物品在有效租赁订单中是否存在时间重叠。
订单金额由租金或售价、押金和租赁天数计算得到。订单保存后处于待支付状态，系统向买家发送“订单创建成功”消息，向卖家发送“收到新的订单申请”消息。后续状态更新时，系统同步租赁记录和物品状态，并在订单完成时调用信用规则为双方增加信用分。若用户在已支付或履约阶段取消订单，系统可根据业务规则记录违约信用扣分。

### 6.4 支付与退款实现

支付模块由 PaymentService、PaymentGateway、LocalPaymentGateway 和 WechatPayGateway 组成。PaymentService 是业务入口，负责订单归属校验、支付流水创建、回调处理、查询和退款；PaymentGateway 是支付适配接口；WechatPayGateway 面向生产微信支付；LocalPaymentGateway 面向本地和测试环境。
创建支付时，系统查找订单最近一条支付流水，若不存在处理中流水则创建新的 PROCESSING 流水。随后调用支付网关返回 timeStamp、nonceStr、package、signType、paySign 和 paymentNo。支付回调解析后，系统根据 out_trade_no 找到支付流水，检查订单是否存在，检查金额是否与本地记录一致。若金额不一致，流水标记为失败并记录原因；若交易成功，流水更新为成功并写入 transactionId，同时推动订单进入已支付状态。
退款申请要求订单状态已达到可退款条件，系统写入 REFUND 类型流水，并将订单状态更新为退款中。若已有处理中的退款流水，则直接返回原退款信息，避免重复申请。

### 6.5 本地支付模拟实现

为了在没有真实微信支付商户凭证的情况下测试完整流程，系统提供本地支付模拟能力。非生产环境创建支付时，LocalPaymentGateway 返回 LOCAL_PAY_SIGN 开头的支付签名。小程序检测到该签名后弹出“本地支付模拟”确认框，用户确认后调用 /api/payment/local/confirm/{paymentNo}。该接口只在非生产 profile 注册，并且要求用户 token。
后端本地确认接口会校验支付流水归属、订单归属、支付类型、支付状态、订单状态和金额一致性。校验通过后复用真实支付成功逻辑，将支付流水更新为 SUCCESS，将订单状态推进到 PAID，并返回支付单、订单状态和交易流水摘要。该设计避免了旧式前端直接修改订单状态的演示兜底，使开发环境也能验证后端状态机。

### 6.6 信用评价实现

评价模块要求订单已完成，且评价者必须是订单买家或卖家。系统检查同一订单是否已经由当前用户评价，防止重复提交。评价提交后保存评分和内容，并向被评价方发送系统消息。评价结果会触发信用规则，好评可增加信用分，差评和投诉成立可扣减信用分。
信用模块通过 CreditService 统一处理信用分变化。每次变更会保存变更前分值、变更后分值、变化原因和关联订单，形成可追踪的信用流水。信用分设置最小值和最大值，防止异常操作导致分值越界。后台用户管理中也提供信用处理入口，便于运营人员对违约或投诉场景进行人工处理。

### 6.7 消息通知实现

消息模块用于系统通知和用户沟通。订单创建、订单状态更新、订单取消、评价提交等场景会自动发送系统消息。用户之间可通过物品详情或订单详情发起联系消息。消息列表支持分页查询，未读消息可标记为已读。小程序消息中心在非 release 环境可展示演示消息，release 环境则要求登录后访问真实接口。
WebSocket 配置为后续实时消息预留能力，并加入 token 校验。未携带合法 token 的连接不会进入受保护消息通道，避免匿名用户监听消息。

### 6.8 后台管理实现

后台首页展示用户、物品、订单和交易额等关键指标。用户管理页展示昵称、学号、校区、认证状态、信用分和账号状态，支持禁用用户和信用处理。物品管理页展示物品标题、发布者、价格、状态和审核建议，支持审核通过和驳回。订单管理页支持按类型、状态和关键词筛选，详情弹窗展示订单状态、金额、双方信息、租期、支付状态、支付单号和交易流水，并支持管理员推进订单状态。
系统配置页用于维护轮播图、公告、分类、校区和风控规则。系统用户管理页仅超级管理员可访问，支持后台账号新增、编辑、停用和重置密码。前端请求拦截器统一携带 token，并在 401 时清理登录状态并跳转登录页。

### 6.9 文件上传实现

文件上传模块用于物品图片等资源。后端将上传文件保存到配置的 FILE_UPLOAD_PATH，数据库中保存文件访问 URL。Docker 部署时上传目录映射为 uploads volume，管理端 Nginx 将该 volume 以静态路径暴露。该方式实现简单，适合课程设计和本地演示；后续生产环境可替换为 MinIO 或云对象存储。

### 6.10 系统配置持久化实现

早期系统配置若仅使用内存 Map，服务重启后会丢失。当前系统将配置保存到 system_config 表，系统启动时可保留默认 seed，后台修改后持久化到数据库。配置内容包括轮播图、公告、分类、校区和风险规则等。配置持久化提升了后台管理功能的实用性，也为后续运营规则动态调整提供基础。

表 6-1 支付处理关键校验

| 校验点 | 校验目的 | 异常处理 |
| --- | --- | --- |
| 订单归属 | 确认支付发起人为买家 | 拒绝支付或退款 |
| 订单状态 | 确认订单处于待支付或可退款状态 | 返回业务异常 |
| 支付金额 | 防止回调金额被篡改或不一致 | 标记流水失败，不更新订单 |
| 流水状态 | 保证重复回调幂等 | 成功流水直接返回 |
| 运行环境 | 本地确认接口仅非生产启用 | prod profile 不注册接口 |

## 7 系统测试与结果分析

### 7.1 测试目标

测试目标是验证系统核心业务流程可用、权限边界可靠、支付状态机正确、构建部署可重复。由于系统涉及小程序、管理端和后端三部分，测试既包括后端单元测试，也包括前端构建检查、依赖审计和 Docker 镜像构建。重点关注容易引发严重问题的场景，例如用户越权、后台权限混用、支付重复回调、金额不一致和订单状态事务不一致。

### 7.2 测试环境

后端测试环境使用 Docker Maven 镜像 maven:3.9.9-eclipse-temurin-21，确保与项目 Java 21 要求一致。管理端使用 Node.js 运行 npm install、npm run build 和 npm audit。Docker Desktop 用于验证 docker compose config、后端镜像构建和管理端镜像构建。统一验证脚本 scripts/verify-dev.ps1 将这些步骤串联，降低人工遗漏概率。

### 7.3 单元测试设计

后端单元测试主要覆盖 AuthContext、AdminAccessGuard、PaymentServiceImpl 和部分 Controller 行为。AuthContext 测试验证匿名访问被拒绝、CLIENT token 可获取用户 ID、ADMIN token 可获取管理员 ID、后台 token 不能冒充普通用户。AdminAccessGuard 测试验证 OPERATOR 不能执行超级管理员操作，SUPER_ADMIN 可以通过检查。PaymentServiceImpl 测试覆盖支付创建归属校验、支付流水创建、金额不一致回调、成功后幂等、本地支付确认和待支付订单退款拒绝等场景。

### 7.4 功能测试场景

功能测试包括：用户登录后浏览物品、发布物品并等待审核；管理员审核通过物品后，买家创建订单；订单进入待支付后创建支付单；本地环境通过支付确认接口完成支付；支付成功后订单进入已支付状态，物品状态同步变化；订单完成后用户提交评价，信用分发生变化；后台查看订单详情时能够看到支付摘要。异常场景包括禁用用户访问受保护接口、用户访问他人订单支付信息、重复支付确认、金额不一致回调和普通运营账号访问系统用户管理。

### 7.5 构建与依赖安全测试

管理端执行 npm run build 能够完成 TypeScript 类型检查和 Vite 生产构建。构建过程中提示主 chunk 超过 500KB，这是性能优化提示，不影响功能。执行 npm audit 后发现 axios、vite 及间接依赖存在中高危漏洞，已通过提升 axios 和 vite 版本修复，当前 audit 结果为 0 vulnerabilities。后端通过 Docker/JDK21 执行 mvn test，测试结果为 15 个测试全部通过。

### 7.6 Docker 验证

Docker Compose 配置通过 docker compose config --quiet 验证。后端镜像采用 Maven/JDK21 多阶段构建，docker compose build backend 成功。管理端镜像采用 Node 构建静态资源并复制到 Nginx，docker compose build admin 成功。镜像构建通过说明项目在容器环境中具备可重复构建能力。

### 7.7 测试结果分析

测试结果表明，当前系统已经具备演示和验收所需的核心能力。权限边界、支付幂等和订单流转是系统可靠性的重点，已有测试覆盖主要风险点。系统仍存在进一步提升空间，例如后端尚未引入 Testcontainers 进行真实 MySQL 集成测试，小程序端缺少自动化 UI 测试，管理端尚未进行路由级拆包优化。后续可在 CI 中加入更多接口级和端到端测试，提升生产上线信心。

## 8 系统部署与运行维护

### 8.1 开发环境部署

开发环境需要准备 JDK 21、Maven、Node.js、Docker Desktop 和微信开发者工具。开发者复制 .env.example 为 .env 后，可通过 start-dev 脚本启动 MySQL、Redis、后端和管理端，也可分别启动各服务。后端默认运行在 8081 端口，管理端开发服务器默认运行在 5173 端口。

### 8.2 生产环境配置

生产环境应使用 application-prod.yml，并通过环境变量注入数据库连接、Redis 地址、JWT_SECRET、后台初始密码、微信支付商户号、商户私钥路径、API v3 密钥、回调地址和文件访问域名。生产环境不应使用默认密钥，不应提交真实证书和私钥，不应开启过多 SQL 日志。Swagger 是否开放应通过环境变量控制。

### 8.3 Docker Compose 部署

Docker Compose 默认服务名为 lease-mysql、lease-redis、lease-backend 和 lease-admin-nginx。MySQL 使用 volume 保存数据，Redis 使用 appendonly 持久化，后端挂载 uploads volume 保存上传文件，管理端 Nginx 只读挂载 uploads volume 暴露静态访问。后端依赖 MySQL 和 Redis 健康检查，避免数据库未准备好时启动失败。

### 8.4 日志与监控

当前系统主要使用 Spring Boot 日志输出业务关键事件，例如订单创建、订单状态更新和支付结果处理。生产环境应进一步接入集中日志平台，按 traceId 或 requestId 追踪请求链路。支付回调、订单状态更新、退款申请和后台敏感操作应作为重点日志对象。后续还可引入 Prometheus、Grafana 或云监控平台，观察接口耗时、错误率、数据库连接池和磁盘容量。

### 8.5 数据备份与恢复

MySQL 数据和上传文件是系统需要重点保护的持久化资产。生产环境应定期备份数据库，并对 uploads volume 或对象存储进行备份。恢复流程应包括数据库恢复、文件恢复、服务重启和核心接口验证。由于 Flyway 记录数据库结构版本，恢复后应确认 schema_history 表和应用版本匹配。

### 8.6 上线风险与控制

上线风险主要包括真实支付配置错误、回调地址不可达、JWT 密钥泄露、数据库密码弱口令、文件上传目录权限错误和后台账号权限过大。控制措施包括上线前执行统一验证脚本、使用强密钥、限制服务器防火墙、配置 HTTPS、对支付回调进行验签、定期轮换后台账号密码、对敏感操作保留审计日志。

## 9 总结与展望

### 9.1 工作总结

本文围绕校园个人物品租赁与交易场景，完成了一套由微信小程序、Vue 管理后台和 Spring Boot 后端组成的系统。系统从需求分析出发，设计并实现了用户认证、校园认证、物品发布审核、订单状态流转、支付退款、评价信用、消息通知、后台管理、系统配置和容器化部署等功能。通过 JWT 区分学生用户和后台管理员，通过支付流水和订单状态机保证交易过程可追踪，通过 Flyway 和 Docker Compose 提升环境一致性。

### 9.2 系统特色

本系统的特色主要体现在以下几个方面：第一，面向校园场景设计，结合校区、校园认证和信用分增强信任；第二，支持租赁和出售双模式，不只停留在普通二手交易；第三，支付模块同时兼顾生产微信支付骨架和本地可测试支付状态机；第四，后台管理能力较完整，覆盖用户、物品、订单、统计、配置和系统用户；第五，部署和测试流程较规范，提供容器化配置、数据库迁移和统一验证脚本。

### 9.3 不足之处

当前系统仍有不足。首先，真实微信支付商户环境尚需进一步联调，包括证书轮换、异常通知、退款回调和账务对账。其次，文件存储当前使用本地 volume，面对多实例部署和大规模图片访问时需要替换为对象存储。再次，推荐算法仍以规则和人工筛选为主，缺少基于用户行为的个性化推荐。最后，自动化测试主要集中在后端单元测试和构建验证，前端端到端测试和真实数据库集成测试仍需加强。

### 9.4 未来展望

后续可以从以下方向继续完善：第一，引入 MinIO 或云 OSS 作为文件存储，并增加图片压缩、格式校验和内容安全审核；第二，完善微信支付真实退款、退款回调和对账能力；第三，接入消息推送和实时聊天，提高交易沟通效率；第四，基于浏览、收藏、下单和评价数据构建推荐模型；第五，引入 Testcontainers、MockMvc、Playwright 等测试工具，建立端到端自动化测试；第六，增加运营审计、风控策略和数据看板，使系统逐步接近生产级校园服务平台。
